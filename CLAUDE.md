# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

Mundana is an offline-first PWA for a food shop, with two independent modules: **recipe costing** (costos) and **stock**. Phases 0–4 (skeleton, costos, stock, backup, PWA) are implemented (Phase 4's manual browser checks are pending with the user); Phase 5 (polish) is next. `docs/plan.md` (in Spanish) is the source of truth for scope, stack, data model, formulas and phased checklist — read it before starting work, and tick its checkboxes as phases are completed.

## Keeping this file current

Update this CLAUDE.md in the same change whenever something it describes changes: new or renamed commands/npm scripts, added dependencies, architecture or folder-structure decisions, new domain invariants, or when a planned item becomes real (e.g. drop "planned"/"doesn't exist yet" notes once the code lands). Keep it concise and non-obvious; don't duplicate `docs/plan.md`.

## Environment

Claude runs inside the `mundana/site` Docker container (`docker/devel.sh`, repo mounted at `/opt/mundana/site`). **No browser is installed and none can be installed.** All automated tests must run in Node (Vitest, `fake-indexeddb`, optionally jsdom/happy-dom) — never Playwright, Puppeteer, Selenium or a real browser. Anything that needs a real browser (PWA install, real offline start, SW update flow, visual/keyboard UX, backup download/file picker) must be reported explicitly as **untested in browser**, with a short list of manual steps for the user.

## Commands

Host (outside the container):
- `make docker` — build the `mundana/site` image
- `docker/devel.sh` — interactive dev container (Claude config persisted under `~/Docker/claude`)
- `docker/run.sh` — run the Vite dev server on `127.0.0.1:5173`

Container:
- `make check` — shellcheck all tracked `.sh` files + `py_compile` of `release.py` / `upgrade.py` (those scripts don't exist yet)
- `make test` — `npm run check` (types) + `npm run test`
- `make ci-check` — `check` + `npm ci` + tests
- `make build` / `make dev` — `npm run build` / `npm run dev`
- Single test: `npx vitest run src/lib/db.test.ts` or `npx vitest run -t "test name"`

npm scripts: `check` = `svelte-check --fail-on-warnings` (app, `tsconfig.json`) + `tsc` on `vite.config.ts` and `test/` (`tsconfig.node.json`); `test` = `vitest run` (node env, `src/**/*.test.ts` + `test/**/*.test.ts`, config lives in `vite.config.ts`). `test/` holds Node-side tests (manifest, and `dist.test.ts`, which runs a real `vite build` into a temp dir); they're type-checked by `tsconfig.node.json` (`@types/node`), while `src/` stays DOM-only. Icons in `public/icons/` are generated by `node scripts/iconos.mjs` (committed output). CI (`.github/workflows/deploy.yml`) runs check/test/build and deploys `dist/` to Pages on push to `main`.

## Architecture

- **Stack**: TypeScript + Svelte + Vite, static site deployed to GitHub Pages via GitHub Actions. The repo is the **organization site** `mundana-cositas-buenas.github.io`, so the app is served at the domain root: `base: '/'`, and manifest/SW paths are root-relative (no repo prefix). Minimal dependencies: no UI/state/date/chart libraries, no Dexie, no `vite-plugin-pwa`. Single hand-written global CSS file, system fonts.
- **Pure logic outside components**: all business logic lives in plain TS modules (`src/lib/units.ts`, `money.ts`, `texto.ts`, `campos.ts`, `db.ts`, `backup.ts`, `csv.ts`, and per module `calc.ts`/`logic.ts`, `validar.ts`, `repo.ts`, `csv.ts`). Svelte components only display and call into them. This is what makes browserless testing possible.
- **Module layout**: per module, `types.ts` (records), `calc.ts`/`logic.ts` (pure math), `validar.ts` (form strings → records; forms keep numbers as typed text so calc can update live, invalid fields become `NaN` which calc reports as a line error), `repo.ts` (IDB access, multi-store ops in one `DB.tx`), and `*View.svelte`. Field parsing shared by both modules (`leerNumero`, `leerPesos`, `numeroEditable`, `nombreRepetido`, `porNombre`, `Errores`/`Validado`) lives in `src/lib/campos.ts` — modules must not import from each other.
- **Number input**: text inputs with `inputmode="decimal"` parsed by `parseDecimal`/`parsePesos` (Argentine style: `1.234,56`; a lone `.` + 3 digits is thousands), not `type=number`. Pass `$state.snapshot(...)` or plain copies to IDB — Svelte proxies aren't structured-cloneable.
- **Persistence**: `src/lib/db.ts`. Schema changes = append a function to `MIGRATIONS` (index i upgrades v i → i+1; `DB_VERSION` = its length); never edit a released migration. `DB.put` stamps `actualizadoEn`; multi-store atomic writes go through `DB.tx` with `idbRequest` — don't `await` non-IDB promises inside it or the transaction auto-commits. Views get the connection via `getDB()`. Tests use `import 'fake-indexeddb/auto'` and a unique DB name per test.
- **Navigation**: hash routes (`#/costos`, `#/costos/insumos`, `#/costos/receta/<id>`, `#/stock`, `#/stock/movimientos`, `#/stock/alertas`, `#/stock/producto/<id>`, `#/backup`) parsed by `src/lib/nav.ts` (`seccionDesdeHash` + `subruta`); no router lib, no server rewrites needed.
- **Nav badge**: `App.svelte` shows the low-stock count; every write in `src/stock/repo.ts` dispatches `'cambio'` on `cambiosStock` so it refreshes. Any new code that writes `productos`/`movimientos` must dispatch it too (`importar` in `backup.ts` does).
- **The two modules are not related**: recipes never touch stock; recipe ingredients (insumos) and stock products (productos) are separate catalogs.
- **PWA is core, not optional**: `public/manifest.webmanifest` (relative `start_url`/`scope`), `src/pwa/`: `logic.ts` (pure: cache naming/cleanup, precache list, FNV version, fetch strategy), `sw.ts` (thin worker wrapper, local minimal worker types), `registro.ts` (page-side registration + update notices via `avisosVersion`), `ediciones.ts` (unsaved-input tracking so "Recargar" asks first). The `mundana-precache` plugin in `vite.config.ts` emits `sw.js` at the root and replaces `__PRECACHE__`/`__VERSION__`; it **errors if sw.js imports a shared chunk**, so page code may only `import type` from `src/pwa/logic.ts`. No SW in dev. The new SW waits (no auto `skipWaiting`); reload only after the user clicks. No runtime network dependencies (no CDN, remote fonts, analytics) — `test/dist.test.ts` enforces it.
- **Backup is mandatory**: data lives only in the browser. `src/lib/backup.ts` exports/validates/imports every data store (`STORES`; `meta` excluded) and tracks the last backup date in `meta`; `src/backup/BackupView.svelte` adds preview, auto-export before import and CSV downloads (`src/lib/descarga.ts`, browser-only); `App.svelte` shows the 7-day staleness warning. Adding a store or changing record fields means updating `STORES`/`esquemaDe` in `backup.ts`, and bumping its `VERSION` (with an upgrade path in `leerBackup`) if old files would no longer validate.

## Domain invariants

- Money is stored as integer cents; format only on display.
- Recipe cost is **never stored** — always computed, so ingredient price changes propagate.
- Current stock is **never stored as an editable number** — it is the sum of `movimientos` (entrada +, venta −, ajuste signed). Movements are never edited; "anular" sets `anuladoEn` and the movement stops counting but stays in the history.
- Stock alert = active product with stock ≤ `stockMinimo` (bajo) or ≤ 0 (agotado); see `src/stock/logic.ts`.
- Unit conversions only within a family (mass g/kg, volume ml/l, count u); mixing families is an error shown on the line.
- Deleting an ingredient used by a recipe is blocked (`borrarInsumo` throws `InsumoEnUso`, via the `recetaLineas.insumoId` index).
- Recipe lines are ordered by their `orden` field.
- Cost formulas are in `docs/plan.md`; reference test: flour at $1000/kg, 100 g in a recipe → $100.
